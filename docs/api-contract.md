# Conversa API Contract

> **Status: Draft — requires agreement between frontend and backend developers.**
> No endpoint below (other than `GET /api/health`) is implemented yet. Nothing in this document has been tested. Examples are illustrative only.

- **Base URL (local):** `http://localhost:5000/api`
- **Frontend:** `client/` (calls go through `client/src/services/`)
- **Backend:** `server/` (routes → controllers → services)

## 1. Conventions

| Topic | Convention |
|---|---|
| Format | JSON in and out. `Content-Type: application/json`. |
| Field names | `camelCase`. Frontend and backend must use identical names. |
| IDs | Opaque strings generated by the server (e.g. `"ord_1042"`). Clients must not parse or generate them. |
| Timestamps | ISO 8601 in UTC with `Z` (e.g. `"2026-10-21T14:00:00Z"`). Unknown/unset → `null`, never an empty string. |
| Durations | Integer **minutes** (`prepTimeMinutes`, `pendingMinutes`, …). The UI may display hours. |
| Optional fields | Always present in responses; unknown values are `null`. Requests may omit optional fields. |
| Enums | Lowercase `snake_case` strings, exactly as listed. The UI maps them to display labels. |
| Single resources | Returned as a bare object (no envelope). |
| Lists | Returned as `{ "items": [...], "page": 1, "pageSize": 20, "total": 57 }`. |
| Auth | Out of scope for this draft. To be agreed before any non-demo deployment. |

### Error format

All errors use this shape and an appropriate HTTP status:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "details": [{ "field": "quantity", "message": "Must be a positive number." }]
  }
}
```

`details` is optional. Codes: `VALIDATION_ERROR` (400/422), `NOT_FOUND` (404), `CONFLICT` (409), `INTEGRATION_UNAVAILABLE` (503), `AI_UNAVAILABLE` (503), `INTERNAL_ERROR` (500).

Clients must show API failures as errors. They must never silently substitute mock data (demo mode is an explicit client setting, `VITE_USE_MOCK`).

## 2. Order schema (Draft)

| Field | Type | Required on create | Server-generated | Notes |
|---|---|---|---|---|
| `id` | string | no | **yes** | Never accepted from client. |
| `customerName` | string | **yes** | no | 1–120 chars after trim. |
| `source` | enum | no (default `manual`) | no | `manual` \| `whatsapp` \| `instagram` |
| `item` | string | **yes** | no | Product/service, 1–200 chars. |
| `quantity` | number | no (default `1`) | no | Must be `> 0`. |
| `price` | number or null | Agreed total for the whole order. Optional; used for revenue in Insights. |
| `prepTimeMinutes` | integer \| null | no | no | `>= 0` when set. `null` = not yet estimated. |
| `deadline` | string \| null | no | no | ISO 8601 or `null`. |
| `status` | enum | no (default `pending`) | no | `pending` \| `confirmed` \| `in_progress` \| `completed` \| `cancelled` |
| `paymentStatus` | enum | no (default `unverified`) | no | `unverified` \| `pending` \| `verified` \| `rejected` |
| `createdAt` | string | no | **yes** | ISO 8601. |
| `updatedAt` | string | no | **yes** | ISO 8601. |
| `risk` | enum \| null | no | **yes (computed)** | `low` \| `medium` \| `high`; `null` if it cannot be computed (e.g. no deadline or prep time). Read-only; ignored if sent. |

Notes:
- Unknown or missing `prepTimeMinutes`/`deadline` is valid. Orders missing either are **excluded from capacity and risk calculations** and reported in `unscheduledOrders` (see planner) instead of being guessed.
- `paymentStatus` is only changed by a seller action. AI/OCR output must never set it to `verified`.
- Unknown request fields are rejected with `VALIDATION_ERROR`.

### Workload logic (shared by dashboard and planner)

Both endpoints must use the same function so figures always agree:

1. **Pending workload** = orders with `status` in `pending`, `confirmed`, `in_progress` **and** non-null `prepTimeMinutes`. `completed` and `cancelled` are always excluded.
2. `pendingMinutes` = sum of `prepTimeMinutes` over those orders. **Open question:** whether `prepTimeMinutes` is per unit or per order. *Draft assumption: it is the total for the whole order, so `quantity` is not multiplied.*
3. **Available capacity** comes from the seller's working-hours settings (not yet defined — see §9).
4. **At risk** = an open order whose deadline cannot be met given capacity before it. Exact thresholds for `medium`/`high` are backend-defined and must be documented in code when implemented.

## 4. Dashboard

### `GET /api/dashboard`

Purpose: order statistics, workload summary, urgent orders and prioritised recommendations for the Dashboard page.

Request: no parameters.

Example request:
```http
GET /api/dashboard
```

Success `200`:
```json
{
  "stats": { "total": 24, "pending": 7, "inProgress": 6, "completed": 8, "atRisk": 3 },
  "workload": {
    "pendingMinutes": 1860,
    "availableMinutes": 2400,
    "daily": [
      { "date": "2026-10-19", "plannedMinutes": 360, "capacityMinutes": 360 },
      { "date": "2026-10-20", "plannedMinutes": 540, "capacityMinutes": 360 }
    ]
  },
  "urgentOrders": [
    {
      "id": "ord_1042", "customerName": "Aanya Sharma", "item": "Custom birthday cake (2 kg)",
      "deadline": "2026-10-19T18:00:00Z", "prepTimeMinutes": 240,
      "status": "in_progress", "risk": "high"
    }
  ],
  "upcomingDeadlines": [
    { "id": "ord_1042", "customerName": "Aanya Sharma", "deadline": "2026-10-19T18:00:00Z" }
  ],
  "recommendations": [
    { "id": "rec_1", "priority": "high", "action": "Start ord_1042 now",
      "reason": "Needs 4h of prep and is due in 5h — no buffer left.", "orderId": "ord_1042" }
  ]
}
```

Status codes: `200`, `500`.

Error example (`500`):
```json
{ "error": { "code": "INTERNAL_ERROR", "message": "Could not build dashboard." } }
```

Rules:
- `stats.total` counts all orders; `pending`/`inProgress` map to statuses `pending`+`confirmed` / `in_progress`; `completed` maps to `completed`. `cancelled` orders are counted in `total` only. *(Draft — confirm.)*
- `stats.atRisk` counts open orders with `risk` of `medium` or `high`. *(Draft — confirm.)*
- `workload` must equal the corresponding `planner` totals (shared logic above).
- `urgentOrders` and `upcomingDeadlines` contain open orders only, sorted by `deadline` ascending; the server caps list lengths (suggested: 5).
- `recommendations` are sorted most-urgent first. `priority` is `high` \| `medium` \| `low`. Rule-based logic decides the action; AI may only phrase `reason`.
- Empty state: a seller with no orders gets zeroed `stats`, empty arrays and `200`.

## 5. Orders

### `GET /api/orders`

Purpose: list orders.

Query parameters (all optional):

| Param | Type | Notes |
|---|---|---|
| `status` | enum | Filter by status. Comma-separated for several. |
| `paymentStatus` | enum | Filter by payment status. |
| `source` | enum | Filter by source. |
| `page` | integer | Default `1`. |
| `pageSize` | integer | Default `20`, max `100`. |
| `sort` | string | `deadline` (default, nulls last), `-deadline`, `createdAt`, `-createdAt`. |

Example request:
```http
GET /api/orders?status=pending,confirmed&page=1&pageSize=20
```

Success `200`:
```json
{
  "items": [
    {
      "id": "ord_1042", "customerName": "Aanya Sharma", "source": "whatsapp",
      "item": "Custom birthday cake (2 kg)", "quantity": 1, "prepTimeMinutes": 240,
      "deadline": "2026-10-19T18:00:00Z", "status": "in_progress", "paymentStatus": "pending",
      "risk": "high", "createdAt": "2026-10-17T09:12:00Z", "updatedAt": "2026-10-18T11:03:00Z"
    }
  ],
  "page": 1, "pageSize": 20, "total": 1
}
```

Status codes: `200`, `400` (invalid query), `500`.

Error example (`400`):
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid query.", "details": [{ "field": "status", "message": "Unknown status 'done'." }] } }
```

### `POST /api/orders`

Purpose: create an order (typically after the seller reviews an AI draft or enters one manually).

Body: order fields per §2. Required: `customerName`, `item`.

Example request:
```http
POST /api/orders
Content-Type: application/json

{
  "customerName": "Rohan Mehta", "source": "instagram", "item": "Gift hamper",
  "quantity": 3, "prepTimeMinutes": null, "deadline": "2026-10-20T12:00:00Z"
}
```

Success `201` (with `Location: /api/orders/ord_1045`): the full created order.
```json
{
  "id": "ord_1045", "customerName": "Rohan Mehta", "source": "instagram", "item": "Gift hamper",
  "quantity": 3, "prepTimeMinutes": null, "deadline": "2026-10-20T12:00:00Z",
  "status": "pending", "paymentStatus": "unverified", "risk": null,
  "createdAt": "2026-10-19T08:00:00Z", "updatedAt": "2026-10-19T08:00:00Z"
}
```

Status codes: `201`, `400`/`422` (validation), `500`.

Error example (`422`):
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Request validation failed.", "details": [{ "field": "quantity", "message": "Must be a positive number." }] } }
```

Rules: server generates `id`, `createdAt`, `updatedAt`, `risk`. Missing `prepTimeMinutes`/`deadline` are accepted and stored as `null`. Creating an order is always an explicit client action; the AI endpoint never calls this.

### `GET /api/orders/:id`

Purpose: fetch one order.

Example request: `GET /api/orders/ord_1045`

Success `200`: the full order object (as above).

Status codes: `200`, `404`, `500`.

Error example (`404`):
```json
{ "error": { "code": "NOT_FOUND", "message": "Order 'ord_9999' not found." } }
```

### `PATCH /api/orders/:id`

Purpose: partially update an order (including status and payment status changes).

Body: any subset of `customerName`, `item`, `quantity`, `prepTimeMinutes`, `deadline`, `status`, `paymentStatus`, `source`. `id`, `createdAt`, `updatedAt`, `risk` are read-only; sending them is a `VALIDATION_ERROR`. Send `null` to clear `prepTimeMinutes`/`deadline`.

Example request:
```http
PATCH /api/orders/ord_1045
Content-Type: application/json

{ "prepTimeMinutes": 300, "status": "confirmed" }
```

Success `200`: the full updated order.

Status codes: `200`, `400`/`422`, `404`, `409` (invalid status transition), `500`.

Error example (`409`):
```json
{ "error": { "code": "CONFLICT", "message": "Cannot change a cancelled order to 'in_progress'." } }
```

Rules: `completed` and `cancelled` are terminal; further status changes are rejected with `409`. *(Draft — confirm.)* Changing `paymentStatus` to `verified` is a seller action only. No `DELETE` endpoint in this draft — use `status: "cancelled"`.

## 6. AI order extraction

### `POST /api/ai/extract-order`

Purpose: turn a customer message into a **draft** order for seller review. **Does not create or save anything.**

Body:

| Field | Type | Required | Notes |
|---|---|---|---|
| `message` | string | **yes** | 1–4000 chars. |
| `source` | enum | **yes** | `manual` \| `whatsapp` \| `instagram` |
| `customerName` | string | no | Hint if known from the conversation. |
| `referenceTime` | string | no | ISO 8601; used to resolve "tomorrow", "Friday". Defaults to server time. |

Example request:
```http
POST /api/ai/extract-order
Content-Type: application/json

{ "message": "Hi! Can I get 2 dozen cupcakes by Friday evening? - Priya", "source": "whatsapp" }
```

Success `200`:
```json
{
  "draft": {
    "customerName": "Priya", "source": "whatsapp", "item": "Cupcakes (2 dozen)",
    "quantity": 24, "prepTimeMinutes": null, "deadline": "2026-10-23T18:00:00Z"
  },
  "missingFields": ["prepTimeMinutes"],
  "uncertainties": [
    { "field": "deadline", "message": "'Friday evening' interpreted as 18:00 local time; confirm." },
    { "field": "quantity", "message": "'2 dozen' interpreted as 24 units; confirm whether quantity counts boxes or items." }
  ],
  "isDraft": true
}
```

Status codes: `200`, `400`/`422` (bad request), `503` (`AI_UNAVAILABLE`), `500`.

Error example (`503`):
```json
{ "error": { "code": "AI_UNAVAILABLE", "message": "The AI service is currently unavailable. You can enter the order manually." } }
```

Rules:
- `draft` uses the order field names from §2 but has no `id`, `status`, `paymentStatus`, `risk`, or timestamps.
- Anything the model could not determine is `null` and listed in `missingFields`. Ambiguous interpretations go in `uncertainties`. The model must not invent values.
- The server validates model output against the schema before returning it; invalid output yields `503`/`AI_UNAVAILABLE`, not a malformed draft.
- Nothing is persisted. The client saves via `POST /api/orders` only after seller approval.

## 7. Workload planner

### `GET /api/planner`

Purpose: scheduled orders, workload, available capacity, deadline risks and recommendations.

Query parameters (optional): `from` (ISO date, default today), `days` (integer, default `7`, max `30`).

Example request:
```http
GET /api/planner?from=2026-10-19&days=7
```

Success `200`:
```json
{
  "range": { "from": "2026-10-19", "days": 7 },
  "workload": { "pendingMinutes": 1860, "availableMinutes": 2400, "utilisationPercent": 78 },
  "days": [
    {
      "date": "2026-10-19", "plannedMinutes": 360, "capacityMinutes": 360,
      "orders": [{ "id": "ord_1042", "customerName": "Aanya Sharma", "item": "Custom birthday cake (2 kg)", "scheduledMinutes": 240 }]
    }
  ],
  "risks": [
    { "orderId": "ord_1039", "risk": "medium", "reason": "Tuesday is 180 minutes over capacity before this deadline." }
  ],
  "unscheduledOrders": [
    { "id": "ord_1045", "reason": "missing_prep_time" }
  ],
  "recommendations": [
    { "id": "rec_2", "priority": "high", "action": "Move ord_1039 preparation to Wednesday",
      "reason": "Tuesday is over capacity; Wednesday has 120 minutes free.", "orderId": "ord_1039" }
  ]
}
```

Status codes: `200`, `400` (invalid query), `500`.

Error example (`400`):
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid query.", "details": [{ "field": "days", "message": "Must be between 1 and 30." }] } }
```

Rules: uses the shared workload logic (§2). `unscheduledOrders[].reason` is `missing_prep_time` \| `missing_deadline` \| `missing_both`. Scheduling and risk are computed by a rule-based engine; AI may only explain.

### `POST /api/planner/simulate`

Purpose: preview the effect of hypothetical changes **without modifying saved orders**.

Body:

| Field | Type | Notes |
|---|---|---|
| `changes` | array | **Required**, 1–20 items. |
| `changes[].type` | enum | `add_order` \| `update_order` \| `cancel_order` |
| `changes[].orderId` | string | Required for `update_order`/`cancel_order`. |
| `changes[].order` | object | Required for `add_order` (order fields per §2). For `update_order`, only the changed fields (e.g. `deadline`, `prepTimeMinutes`). |
| `from`, `days` | | Same as `GET /api/planner`. |

Example request:
```http
POST /api/planner/simulate
Content-Type: application/json

{
  "changes": [
    { "type": "add_order", "order": { "customerName": "Meera Iyer", "item": "Wedding favours x50", "prepTimeMinutes": 480, "deadline": "2026-10-22T10:00:00Z" } },
    { "type": "update_order", "orderId": "ord_1039", "order": { "deadline": "2026-10-23T10:00:00Z" } }
  ],
  "from": "2026-10-19", "days": 7
}
```

Success `200`: same shape as `GET /api/planner`, computed on the hypothetical state, plus a comparison against the current state:
```json
{
  "simulated": true,
  "planner": { "range": {}, "workload": {}, "days": [], "risks": [], "unscheduledOrders": [], "recommendations": [] },
  "comparison": {
    "pendingMinutesDelta": 480,
    "newRisks": [{ "orderId": "ord_1047", "risk": "high", "reason": "Capacity exhausted by the added order." }],
    "resolvedRisks": [{ "orderId": "ord_1039" }]
  }
}
```
(`planner` is abbreviated above; it contains the full planner response.)

Status codes: `200`, `400`/`422`, `404` (unknown `orderId`), `500`.

Error example (`404`):
```json
{ "error": { "code": "NOT_FOUND", "message": "Order 'ord_9999' not found." } }
```

Rules: **read-only** — no order, task or schedule is persisted; a repeat call with the same input and unchanged data returns the same result. Hypothetical orders have no `id` in the response; they are referenced by their index in `changes` (e.g. `"orderId": "change_0"`). Applying a simulated change is a separate explicit `POST`/`PATCH /api/orders` call.

## 7a. Insights dashboard

### `GET /api/analytics/summary?range=7|30&dataset=all|real|demo`

Powers the Insights page. Implemented in `server/services/insightsService.js` (pure: orders, settings, days, now). Orders belong to the period by the day they were **received** (`createdAt`, business timezone, today included); cancelled orders are excluded everywhere; each order is counted once.

Returns `kpis` (`totalRevenue`, `totalOrders`, `completedOrders`, `averageOrderValue`), `trend` (one `{ date, orders, revenue }` per day), `topProducts` (top 3 by units: `product`, `units`, `orders`, `revenue`), `insights` (up to 3, each with `title`, `finding`, `action`, `link`), `datasets` and `basis`.

- **Revenue** is booked sales: the sum of the optional order field `price` (the agreed total for the whole order, `number >= 0` or `null`). Unpriced orders are left out and counted separately; with no priced order, revenue and average order value are `{ available: false, reason }`.
- **Comparison** with the previous period of the same length is returned only when that period has at least 3 orders (3 priced orders for money figures); otherwise `comparison: { available: false, reason }`.
- **Insights** are produced only from supporting data: scheduler overload (`computePlan`), a clear busiest ordering weekday (5+ orders), a clear best seller, and unpriced orders.
- Errors: `400 VALIDATION_ERROR` for a `range` other than 7 or 30, or an unknown `dataset`.

## 7b. Monthly analytics

### `GET /api/analytics/monthly?month=YYYY-MM&dataset=all|real|demo`

Business insights for one calendar month in the business timezone (`month` defaults to the current month; `dataset` defaults to `all`: `real` excludes orders whose notes start with `[DEMO]`, `demo` includes only those, and the filter is applied before every metric. The response carries `datasets: { real, demo, selected }` with the order counts. An invalid value returns `400 VALIDATION_ERROR`). Implemented by `server/services/analyticsService.js` (pure function of orders, settings, month and now). The in-browser demo backend calls the same function, so demo and live agree.

Every metric is either `{ available: true, value, ... }` or `{ available: false, reason }`. A metric is unavailable when the order schema cannot support it; the API never returns an estimated or illustrative value in its place.

| Section | Fields | Basis |
|---|---|---|
| `quality` | `mode` (`real` \| `demo` \| `mixed` \| `empty`), `ordersInMonth`, `historyMonths`, `incomplete[]` | `[DEMO]` notes mark demo orders |
| `overview` | `received` (+`previous`, `change`), `completed`, `pending`, `cancelled` | orders whose `createdAt` is in the month, by current status. `change` needs 3+ orders in the previous month |
| `sales` | `receivedByWeek`, `bestSellers`, `busiestWeek`, `customers` | grouped by product name; new vs returning only from `customerContact` (never names) |
| `fulfilment` | `dueByWeek`, `due`, `dueCompleted`, `overdueOpen`, `atRisk`, `carryover` | orders whose `deadline` is in the month. `atRisk` is the scheduler's PREDICTION, not an actual late delivery |
| `payments` | `statusCounts`, `recordedNotes` | `paymentStatus` counts; `paymentEvidence` amounts are seller notes, not verified money |
| `customers` | `repeatCustomers`, `followUps` | needs `customerContact`; follow-ups come from open orders only |
| `capacity` | `days[]` (14 days from now), `overloadedDates`, `sameDayDeadlines`, `spareMinutes` | `computePlan`; always the next 14 days |
| `opportunities[]` | `insight`, `evidence`, `why`, `action`, `link` | only generated when the data supports them |

Always `available: false` today, with the field each one needs: `overview.revenue`, `outstandingBalance` and `sales.weeklyRevenue`, `averageOrderValue`, `customers.topBySpend` (order **price**); `overview.onTimeRate`, `fulfilment.averageFulfilmentTime`, `lateCompletions` (**completedAt**); `fulfilment.delayReasons` (**delayReason**); `payments.advances`, `refunds`, `outstanding` (**amount paid / refunds**); `payments.profit` (**costs**); `customers.complaints` (**complaint / rework record**); `customers.reorderReminders`, `capacity.recurringDelays` (**several months of history with completion times**).

## 8. Integrations

> **Not implemented.** Real WhatsApp and Instagram flows use the Meta platform (OAuth / Embedded Signup, webhooks, app review and permissions). The routes and payloads below are the *intended* shape only and **must be verified against the implemented Meta integrations** before the frontend relies on them. Until then, the backend should report `demo` or `unavailable`, never `connected`.

Integration `status` values:

| Value | Meaning |
|---|---|
| `connected` | A real account is linked and verified. |
| `disconnected` | Supported, but no account is linked. |
| `unavailable` | Supported in principle, but cannot be used now (missing config/permissions, API error). `statusReason` explains. |
| `demo` | Sample data only; no real account. UI must label it as demo. |

```json
  "items": [

    { "channel": "instagram", "status": "unavailable", "statusReason": "Meta app permissions not configured.", "accountLabel": null, "lastSyncAt": null }
  ]
}
```

Status codes: `200`, `500`.

Error example (`500`):
```json
{ "error": { "code": "INTERNAL_ERROR", "message": "Could not load integrations." } }
```

### `POST /api/integrations/instagram/connect`

Purpose: start connecting a channel. *Intended flow (draft):* the client calls the endpoint; the backend returns either a Meta authorisation URL to redirect the seller to, or an error explaining why connecting is unavailable. Completion (OAuth callback / webhook verification) happens on the backend and is **not** part of this contract yet.


```json

```

Rules: secrets and tokens are server-side only and never returned. Responses must not claim `connected` until the backend has verified the account.

## 9. Discrepancies and open questions (for review)

Compared against the current frontend (`client/src/mock/dashboardData.js`, `client/src/pages/Dashboard.jsx`, `client/src/services/dashboardService.js`). **No application code was changed**; the frontend will need updating once these are agreed.

| # | Frontend today | This draft | Proposed resolution |
|---|---|---|---|
| 1 | Workload in **hours**: `pendingHours`, `availableHours`, `daily[].hours/capacity` | Integer **minutes**: `pendingMinutes`, `availableMinutes`, `plannedMinutes/capacityMinutes` | Use minutes in API; convert for display in the client. |
| 2 | `daily[].label` (`"Mon"`) | `daily[].date` (ISO date) | Client derives weekday label from `date`. |
| 3 | Orders use `customer`, `prepHours` | `customerName`, `prepTimeMinutes` | Adopt contract names. |
| 4 | `status` is a display label (`"Preparing"`, `"Payment Received"`) | Enum (`in_progress`, …) plus separate `paymentStatus` | Client maps enums to labels. README lifecycle stages (Enquiry … Follow-up) are **not** in the proposed enum — decide whether they are statuses, UI groupings, or out of MVP scope. |
| 5 | `deadline` always set | `deadline` may be `null` | Client must handle `null`. |
| 6 | Mock order IDs like `ORD-1042` | Opaque server IDs (`ord_1042` in examples) | Treat IDs as opaque; don't display raw IDs if format changes. |
| 7 | `risk` = `high`/`medium` only | `low`/`medium`/`high`/`null` | Client handles all values. |
| 8 | Recommendations lack `orderId` | Optional `orderId` added | Additive; no break. |
| 9 | Dashboard response is a bare object | Same (bare object); lists use `{ items, page, pageSize, total }` | Aligned. |
| 10 | `stats` keys `total/pending/inProgress/completed/atRisk` | Same | Aligned; mapping of `confirmed` → `pending` needs confirmation. |

Open questions:
1. Is `prepTimeMinutes` per order or per unit (§2 step 2)?
2. How are working hours/capacity configured (no settings endpoint exists in this draft)?
3. Thresholds for `risk` levels.
4. Authentication and multi-seller data isolation.

## 10. Change management

- This file is the single source of truth for routes and JSON field names shared by `client/` and `server/`.
- Any change to a route, request field, response field, enum value or error code requires agreement between **both** the frontend and backend developers, recorded in the same pull request that updates this document.
- Additive, optional response fields are preferred over breaking changes. Breaking changes must be announced before they are merged.
- When a draft section is implemented and tested, change its label from **Draft** to the verified state and note what was tested.
- Frontend mock data in `client/src/mock/` must mirror the schemas here.
